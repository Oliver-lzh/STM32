# 阶段1数据入口探测开发技能

## 使用场景

当用户准备把 TI `vitalSigns_16xx_dss` 的呼吸/心率算法移植到 RadarBaseboardMCU7 固件时，第一阶段必须先使用本技能。

本阶段目标不是做 Range FFT，也不是直接计算呼吸率和心率，而是先确认英飞凌固件中 `Board_dataCallback(...)` 或 `BoardOutput_onFrame(...)` 收到的数据到底是什么。

必须确认的问题：

- `payload` 是单个 chirp 的原始 ADC 数据。
- 还是多个 chirp 聚合后的 frame 数据。
- 还是上位机或固件配置后的某种数据帧。
- `count` 的单位是字节数、样本数，还是协议层定义的元素数量。
- `channel` 表示雷达通道、数据队列 index，还是其他含义。
- `timestamp` 的变化周期能否代表 chirp 周期或 frame 周期。

本技能用于指导后续代码开发。单独使用本技能时，不应直接改动固件源码。

## 背景依据

当前英飞凌 Avian 数据链路的大致路径是：

```text
DataAvian_readData()
-> 从 Avian FIFO/SPI 读取雷达数据
-> 写入 DataAvian 内部缓冲或队列
-> DataAvian_run()
-> frameCallback(data, frameSize, index, timestamp)
-> Board_dataCallback(payload, count, channel, timestamp)
```

关键源码路径：

```text
sources/sources/stratula/library/platform/DataAvian.c
sources/targets/atmel/subprojects/RadarBaseboardMCU7/Board.c
sources/targets/atmel/subprojects/RadarBaseboardMCU7/BoardOutput.c
sources/targets/atmel/subprojects/RadarBaseboardMCU7/BoardOutput.h
```

TI demo 的生命体征算法不是对每一个 chirp 直接输出呼吸/心率，而是：

```text
多个 chirp 组成 frame/cube
-> 每个 chirp 做 Range FFT
-> frame 结束后选择目标 range bin
-> 每帧提取该 bin 的 I/Q
-> 用慢时间相位估计呼吸/心率
```

所以 RadarBaseboardMCU7 的第一阶段重点是确认“当前拿到的数据是否足够构造 TI 所需的慢时间 I/Q 输入”。

## 目标行为

后续实现阶段一探测功能时，应能在 `DEBUG_TEXT` 模式下看到类似输出：

```text
probe,frame=100,count=4096,channel=0,timestamp=12345678,dt=33333
probe,head=01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F 10
```

输出必须限频，例如每 50 帧或每 100 帧打印一次，不能每帧打印完整 payload。

阶段一只输出摘要：

- 帧计数。
- `count`。
- `channel`。
- `timestamp`。
- 相邻 timestamp 差值。
- 前 16 或 32 字节 payload 的十六进制预览。

阶段一不做：

- 不做 Range FFT。
- 不做 chirp 解析结论硬编码。
- 不做完整 payload 文本打印。
- 不做呼吸率/心率估计。
- 不修改 HAL、ASF、CMSIS、SPI、DMA。

## 关于 DEBUG_TEXT 是否能打印雷达信息

可以打印，但有前提和边界。

### 可以打印的情况

如果固件已经处于 `DEBUG_TEXT` 模式，并且雷达采集已经启动，那么可以用 `BoardOutput_printf(...)` 打印阶段一摘要信息。

推荐只打印少量摘要，不打印完整雷达数据：

```text
count/channel/timestamp
前 16 或 32 字节 payload
每 N 帧打印一次
```

这样做的原因是 USB CDC 文本输出速度远低于雷达数据产生速度。如果把每帧完整 payload 都转成文本打印，很容易导致：

- USB 发送缓冲忙。
- 主循环被拖慢。
- 雷达采集停止或丢帧。
- 固件看起来像卡死。

### 不能混用的情况

`HOST_PROTOCOL` 模式下不能打印普通文本。普通文本会污染官方上位机协议流，导致官方上位机解析失败。

因此：

- `DEBUG_TEXT` 模式：允许打印阶段一探测信息。
- `HOST_PROTOCOL` 模式：保持官方协议，不输出普通文本。

### 需要特别注意的问题

如果雷达采集必须由官方上位机通过 `HOST_PROTOCOL` 下发配置和启动命令，那么纯 `DEBUG_TEXT` 模式下可能不会自动产生雷达帧。

这种情况下有三种后续方案：

1. 在固件里临时加入固定雷达配置和自动启动采集，只用于阶段一探测。
2. 先通过官方上位机确认配置参数，再把同等参数固化到调试固件里。
3. 后续设计更安全的运行时模式流程，让配置/启动和调试输出不污染同一个协议流。

第一阶段文档只要求说明这个风险，不要求立刻实现自动启动采集。

## 推荐接入位置

优先接入位置有两个。

### 方案 A：接在 Board_dataCallback(...)

位置：

```text
sources/targets/atmel/subprojects/RadarBaseboardMCU7/Board.c
```

优点：

- 最靠近当前板级数据入口。
- 可以直接拿到 `payload/count/channel/timestamp`。
- 容易确认官方原始数据回调是否触发。

缺点：

- `Board.c` 容易变重。
- 如果直接在这里打印太多，会影响数据回调路径。

### 方案 B：接在 BoardOutput_onFrame(...)

位置：

```text
sources/targets/atmel/subprojects/RadarBaseboardMCU7/BoardOutput.c
```

优点：

- 和 `DEBUG_TEXT` / `HOST_PROTOCOL` 输出策略放在同一层。
- 方便保证 `HOST_PROTOCOL` 下不输出普通文本。
- 后续可以把探测输出封装成板级输出能力。

缺点：

- 如果 `BoardOutput_onFrame(...)` 在 `DEBUG_TEXT` 下直接忽略 payload，需要新增探测逻辑。
- 仍然必须避免在回调路径里做大量字符串格式化。

推荐第一版优先采用方案 B，或者在 `Board_dataCallback(...)` 只调用一个轻量探测入口，例如：

```c
AppRadarProbe_onFrame(payload, count, channel, timestamp);
```

真正打印逻辑可以放到探测模块内部限频执行。

## 建议新增模块

后续实现时，不建议把探测逻辑全部堆到 `Board.c`。

建议新增：

```text
sources/targets/atmel/subprojects/RadarBaseboardMCU7/AppRadarProbe.c
sources/targets/atmel/subprojects/RadarBaseboardMCU7/AppRadarProbe.h
```

建议接口：

```c
void AppRadarProbe_Constructor(void);
void AppRadarProbe_onFrame(const uint8_t *payload,
                           uint32_t count,
                           uint8_t channel,
                           uint64_t timestamp);
```

如果后续希望把打印从数据回调中移出来，可以再加：

```c
void AppRadarProbe_run(void);
```

但第一版可以先只做 `onFrame`，并严格限频打印。

## 打印策略

### 输出频率

建议从保守值开始：

```text
每 100 帧打印一次
```

如果帧率较低，可以改为每 50 帧打印一次。

不建议每帧打印。

### 输出内容

推荐格式：

```text
probe,frame=<frame_counter>,count=<count>,channel=<channel>,timestamp=<timestamp>,dt=<delta_timestamp>
probe,head=<hex bytes>
```

其中：

- `frame_counter` 是固件本地计数。
- `dt` 是当前 timestamp 减去上一次 timestamp。
- `head` 只取 payload 前 16 或 32 字节。

### 输出安全

如果 `BoardOutput_printf(...)` 返回 `E_BUSY`，阶段一探测逻辑应允许丢弃本次打印。

阶段一探测不能因为串口助手没打开、USB 忙、TX buffer 不够而阻塞雷达采集。

## 多 Subagent 分工

后续实现阶段一功能时，使用多 subagent 模式，但最终决策仍由 Root 主控集成者负责。

### Root 主控集成者

职责：

- 冻结阶段一只做数据入口探测，不做算法。
- 决定探测入口放在 `Board_dataCallback(...)`、`BoardOutput_onFrame(...)`，还是新模块。
- 指定每个 Agent 的文件范围和禁止修改范围。
- 合并结果并判断是否可以编译、烧写和手测。

Root 不把最终判断交给子 Agent。

### 实现 Agent

职责：

- 按 Root 指定范围写代码。
- 优先新增 `AppRadarProbe.c/.h`。
- 必要时只做最小调用点修改。
- 不改 HAL、ASF、CMSIS、SPI、DMA。
- 不在 `HOST_PROTOCOL` 模式输出普通文本。

实现重点：

- 记录 frame counter。
- 记录 timestamp 差值。
- 限频打印摘要。
- 只打印 payload 头部少量字节。

### 审查/测试 Agent

职责：

- 检查是否存在 USB CDC 阻塞风险。
- 检查是否在 `HOST_PROTOCOL` 下污染官方协议。
- 检查是否越界读取 payload。
- 检查 `count == 0`、`payload == NULL` 等边界。
- 检查是否在数据回调中做了过重操作。

审查结果必须指出具体文件、函数和风险。

### 构建验证 Agent

职责：

- 检查新增 `.c/.h` 是否加入 Atmel Studio 工程或 Makefile。
- 确认使用 Atmel Studio 自带 ARM GCC 6.3.1。
- 不使用 STM32CubeCLT GCC 13.3.1。
- 验证 Release 和 Debug 编译。
- 检查 `.bin`、`.elf`、`.map` 是否生成。

### 专项分析 Agent

需要时临时启用，负责专项分析：

- `DataAvian_readData()` 的读取单位。
- `frameCallback(...)` 的 `frameSize` 来源。
- `Board_dataCallback(...)` 的回调触发频率。
- `BoardOutput_printf(...)` 在 USB CDC 忙时的返回行为。
- 上位机配置是否影响 payload 格式。

专项分析 Agent 默认只读，除非 Root 明确授权其修改指定文件。

## 实施顺序

推荐后续按以下顺序开发：

1. 确认当前 `Board.c`、`BoardOutput.c`、`BoardOutput.h` 的状态。
2. 确认 `BoardOutput_printf(...)` 只在 `DEBUG_TEXT` 下输出。
3. 新增或规划 `AppRadarProbe.c/.h`。
4. 在数据入口处接入 `AppRadarProbe_onFrame(...)`。
5. 实现限频摘要输出。
6. 编译验证 Release 和 Debug。
7. 烧写后打开串口助手观察 `probe,...` 输出。
8. 根据 `count/timestamp/head` 判断 payload 结构。

## 验证要求

后续代码实现完成后，至少验证：

- `DEBUG_TEXT` 模式下可以看到 `probe,...` 文本。
- `HOST_PROTOCOL` 模式下没有普通文本输出。
- 输出频率受控，不会刷屏。
- payload 头部读取不会越界。
- 串口助手未打开或 USB 忙时固件不应卡死。
- 雷达采集不应因为打印摘要而停止。
- Release 和 Debug 编译均成功。
- `.bin`、`.elf`、`.map` 均正常生成。

## 禁止事项

- 不打印完整 payload。
- 不在 `HOST_PROTOCOL` 模式输出普通文本。
- 不在官方通信协议层里塞入调试文本。
- 不在数据回调里做长时间循环或大块字符串格式化。
- 不直接开始写 Range FFT。
- 不直接移植 TI 心率/呼吸算法。
- 不改底层 HAL、ASF、CMSIS、SPI、DMA。
- 不使用错误工具链编译。

## 当前阶段边界

本文件只是阶段一开发技能说明。当前阶段不修改：

- `Board.c`
- `BoardOutput.c`
- `BoardOutput.h`
- `DataAvian.c`
- 官方通信协议层源码
- 雷达采集底层源码

真正开始实现阶段一数据入口探测时，必须重新确认当前代码状态，再按本技能启用多 subagent 开发和构建验证。
