# 内部启动采集调试入口开发技能

## 使用场景

当需要在 `DEBUG_TEXT` 普通串口调试模式下验证雷达 payload 时使用本技能。目标是不打开官方 Radar Fusion GUI，也能由固件自己完成 BGT60TR13C Raw Data 配置和采集启动，让 `Board_dataCallback(...)` 被真实雷达数据触发，并通过 `AppRadarProbe_onFrame(...)` 打印 payload 摘要。

本技能用于后续源码开发指导。第一版目标是打通“内部启动采集 -> 产生 payload -> 打印 count/dt/head”的调试链路，不做生命体征算法，不改底层 HAL、ASF、CMSIS、SPI、DMA。

## 目标行为

上电后，如果固件处于 `DEBUG_TEXT` 模式，并且检测到 Avian/BGT60TR13C 雷达，则固件自动执行一次内部 Raw Data 采集启动流程。

串口助手预期看到类似输出：

```text
debug-acq,config,start
debug-acq,radar-profile,ok
debug-acq,data-config,ok
debug-acq,start,ok
probe,f=1,cnt=18432,ch=0,ts=...,dt=0,fmt=packed12,head=...
```

如果使用 `DataFormat_Raw16`，则 `cnt` 预期为：

```text
probe,f=1,cnt=24576,ch=0,ts=...,dt=0,fmt=raw16,head=...
```

## 架构位置

本功能放在板级应用层和算法探测层之间，不放在通信协议层。

推荐新增模块：

```text
sources/targets/atmel/subprojects/RadarBaseboardMCU7/AppRadarDebugAcquisition.h
sources/targets/atmel/subprojects/RadarBaseboardMCU7/AppRadarDebugAcquisition.c
```

分层职责：

- `Board.c`：负责检测雷达、保存 Avian 实例、注册数据回调、在主循环调用内部启动状态机。
- `AppRadarDebugAcquisition.c`：负责 DEBUG_TEXT 下的内部雷达 profile 写入、DataAvian 配置和启动采集。
- `AppRadarProbe.c`：只负责 payload 摘要打印，不负责配置雷达。
- `BoardOutput.c`：只负责输出模式、普通文本输出和官方协议输出保护，不承载采集配置逻辑。

不建议放入通信层的原因：

- 通信层的职责是 vendor protocol、请求解析、响应封包和 CRC。
- 内部启动采集是本地调试策略，不是上位机协议。
- 将采集启动放入通信层会让官方协议和普通文本调试互相污染，后续维护风险更高。

## 数据流

内部启动采集后的数据路径如下：

```text
Board_Constructor()
  -> Board_detectRadar(...)
  -> Avian_Constructor(...)
  -> DataAvian_Constructor(...)
  -> DataAvian_setBuffer(...)
  -> DataAvian_initialize(...)
  -> m_data->registerCallback(Board_dataCallback, NULL)
  -> AppRadarDebugAcquisition_Constructor(&m_avian.b_IRadarAvian, m_data, dataIndex)

Board_run()
  -> Platform_run()
  -> DataAvian_run()
  -> AppRadarDebugAcquisition_run()
  -> BoardOutput_run()

Radar IRQ
  -> DataAvian_newDataCallback(...)
  -> DataAvian_readData(...)
  -> DataAvian_run()
  -> Board_dataCallback(payload, count, channel, timestamp)
  -> AppRadarProbe_onFrame(payload, count, channel, timestamp)
  -> BoardOutput_printf(...)
```

## 寄存器配置来源

寄存器配置要分成两类看：

- **控制类寄存器**：例如 `MAIN.FRAME_START`、`MAIN.FIFO_RESET`、`MAIN.FSM_RESET`、`SFCTL`、FIFO 读取地址，这些可以从 BGT60TR13C 数据手册和当前固件源码确认。
- **profile 类寄存器**：例如 PLL 频率斜坡、channel set、chirp/frame timing、IF gain、HPF、Tx power，这些虽然可以按手册公式计算，但第一版不建议手算后直接烧录。更稳的方式是从 Radar Fusion GUI 导出当前配置对应的寄存器序列，再固化到固件。

BGT60TR13C 的 SPI 寄存器是 `7-bit address + 24-bit value`。当前固件已经提供了两种写法：

```c
IRegisters8_32 *registers = radar->getIRegisters(radar);
registers->write(registers, regAddr, value);
```

或者直接使用 Avian SPI 命令：

```c
static const uint8_t g_avianProfile[][4] = {
    AVIAN_WRITE(regAddr, value),
};

IProtocolAvian *protocol = radar->getIProtocolAvian(radar);
protocol->execute(protocol, g_avianProfile, ARRAY_SIZE(g_avianProfile), NULL);
```

`AVIAN_WRITE(address, value)` 的 4 字节格式由源码定义：

```c
byte0 = (address << 1) | 1;
byte1 = (value >> 16) & 0xFF;
byte2 = (value >> 8) & 0xFF;
byte3 = value & 0xFF;
```

## 寄存器写入表

### 当前可以确认的控制寄存器

这些值来自 BGT60TR13C 数据手册和当前固件源码，可以直接写进实现方案。

| 地址 | 寄存器 | 写入/置位值 | 作用 | 源码/手册依据 |
| --- | --- | --- | --- | --- |
| `0x00` | `MAIN` | `0x000001` | 置位 `FRAME_START`，开始 frame generation | `Avian_startData()` |
| `0x00` | `MAIN` | `0x000002` | 置位 `SW_RESET`，软件复位寄存器 | `Avian_reset(true)` |
| `0x00` | `MAIN` | `0x000004` | 置位 `FSM_RESET`，停止 frame generation 的关键位之一 | `Avian_stopData()` |
| `0x00` | `MAIN` | `0x000008` | 置位 `FIFO_RESET`，清空 FIFO | `Avian_stopData()` |
| `0x00` | `MAIN` | `0x00000C` | 同时置位 `FIFO_RESET | FSM_RESET`，停止采集并清 FIFO | `Avian_stopData()` |
| `0x01` | `ADC0` | `0x0A0240` | 当前固件用来识别 BGT60TR13C 的 ADC0 reset value | `Avian_Detect()` |
| `0x06` | `SFCTL` | `0x100000` | 当前固件探测阶段写入的 SPI/FIFO 控制值，用于高速 SPI/QSPI 相关补偿 | `Avian_Detect()` |
| `>=0x60` | FIFO access | `0x60` 作为第一版 FIFO 读取 prefix 地址 | FIFO burst read 入口，`DataAvian_readData()` 会把它作为 burst prefix | 数据手册 register list |

注意：`ProtocolAvian_setBits(...)` 是读-改-写，不是直接把 `MAIN` 整个寄存器覆盖成这些值。实现时优先调用已有接口：

```c
radar->stopData(radar);   /* 内部置位 MAIN.FIFO_RESET | MAIN.FSM_RESET */
radar->startData(radar);  /* 内部先 DataAvian_start，再置位 MAIN.FRAME_START */
```

### 截图配置相关的 profile 寄存器

以下寄存器决定截图中的 `58 GHz -> 63.5 GHz`、`64 samples/chirp`、`64 chirps/frame`、`3 RX`、`Tx power 31`、`IF gain 23 dB`、`HPF 80 kHz` 等 profile 行为。

| 地址范围 | 寄存器 | 对应配置 | 第一版处理策略 |
| --- | --- | --- | --- |
| `0x04` | `PACR1` | PLL analog control，启动前需保证 PLL/OSC 相关路径有效 | 使用 GUI 导出值 |
| `0x05` | `PACR2` | fast-down chirp、divider、`DIVSET` 等 PLL 相关控制 | 使用 GUI 导出值 |
| `0x10..0x12` | `CSU1_0/1/2` | 上升 chirp 的 RX/TX、Tx power、baseband、MADC、IF gain、HPF | 使用 GUI 导出值，手算值只作交叉检查 |
| `0x16` | `CSC1` | channel set 1 使能、`REPC` chirp 重复因子、隔离控制 | 使用 GUI 导出值 |
| `0x2C..0x2F` | `CCR0..CCR3` | frame/chirp timing、shape/frame repetition、start/end delay | 使用 GUI 导出值 |
| `0x30..0x37` | `PLL1_0..PLL1_7` | shape 1 的 FSU/RSU/RTU/APU/FSD/RSD/RTD/SCR | 使用 GUI 导出值 |

可以用手册公式做核对，但不要只靠手算替代 GUI 导出。例如按手册公式对 `58 GHz -> 63.5 GHz`、`36 us` ramp 做候选核对时：

| 寄存器 | 字段 | 候选值 | 含义 |
| --- | --- | --- | --- |
| `PLL1_0` `0x30` | `FSU` | `0xA66AAB` | 58 GHz 起始频率对应的 24-bit two's complement 值 |
| `PLL1_1` `0x31` | `RSU` | `0x000D3F` | 5.5 GHz 带宽、36 us ramp 示例对应的 upchirp ramp step |
| `PLL1_2` `0x32` | `RTU` | `0x00015A` | 36 us ramp 示例对应的 ramp time，十进制 346 |
| `PLL1_3` `0x33` | `APU` | `0x000040` | `64 samples/chirp`，APU 位宽 12 bit |
| `PLL1_4..0x36` | `FSD/RSD/RTD` | `0x000000` | saw-tooth/fast-down 场景下 downchirp 相关字段置 0 |

这个 PLL 示例只说明“如何把频率和 sample 数落到寄存器”，不等价于你 GUI 截图的完整 profile。截图中的 `chirp repetition = 591 us` 和 `frame rate = 12.94 Hz` 还需要 `CCR0..CCR3`、`CSC1.REPC/CCR0.REPT/CCR2.FRAME_LEN` 等共同决定，因此最终实现仍以 GUI 导出的完整寄存器表为准。如果 GUI 导出值和上表候选值不同，以 GUI 导出为准。

### 可作为交叉检查的手算字段

如果 GUI 导出的寄存器值和下面手算值明显不一致，要先暂停分析原因，不要直接烧录。

| 配置 | 寄存器/字段 | 推导值 | 说明 |
| --- | --- | --- | --- |
| `3 RX` | `CSU1_1.BBCH_SEL[22:20]` | `0b111` | Rx1/Rx2/Rx3 对应 baseband/ADC 全开 |
| `Tx power 31` | `CSU1_1.TX_DAC[4:0]` | `31` | TX power 最大等级 |
| `HPF 80 kHz` | `CSU1_2.HPF_SEL1/2/3` | `3` | 数据手册中 `3D` 对应 80 kHz |
| `IF gain 23 dB` | `CSU1_2.HP_GAIN + VGA_GAIN` | 常见组合为 `18 dB + 5 dB` | 三路 RX 一般设置一致，但最终以 GUI 导出为准 |
| `64 samples/chirp` | `PLL1_3.APU[11:0]` | `64` / `0x040` | 单个 RX 的 upchirp ADC sample 数 |
| `64 chirps/frame` | `CSC1.REPC` 或 `CCR0.REPT/CCR2.FRAME_LEN` 组合 | 待 GUI 导出确认 | BGT 的 frame/chirp 结构不是单独一个字段决定 |

### 建议固化的 profile 表结构

后续源码里建议保存“寄存器地址 + 24-bit 值”，而不是直接保存 4 字节命令。这样便于你读表和对照手册：

```c
typedef struct
{
    uint8_t address;
    uint32_t value;
} AppRadarDebugAcquisition_RegisterWrite_t;

static const AppRadarDebugAcquisition_RegisterWrite_t g_profile[] = {
    { 0x06, 0x100000 }, /* SFCTL: use current firmware high-speed SPI setting */
    /* { 0x04, GUI_EXPORT_VALUE }, PACR1 */
    /* { 0x05, GUI_EXPORT_VALUE }, PACR2 */
    /* { 0x10, GUI_EXPORT_VALUE }, CSU1_0 */
    /* { 0x11, GUI_EXPORT_VALUE }, CSU1_1 */
    /* { 0x12, GUI_EXPORT_VALUE }, CSU1_2 */
    /* { 0x16, GUI_EXPORT_VALUE }, CSC1 */
    /* { 0x2C, GUI_EXPORT_VALUE }, CCR0 */
    /* { 0x2D, GUI_EXPORT_VALUE }, CCR1 */
    /* { 0x2E, GUI_EXPORT_VALUE }, CCR2 */
    /* { 0x2F, GUI_EXPORT_VALUE }, CCR3 */
    /* { 0x30, GUI_EXPORT_VALUE }, PLL1_0/FSU */
    /* { 0x31, GUI_EXPORT_VALUE }, PLL1_1/RSU */
    /* { 0x32, GUI_EXPORT_VALUE }, PLL1_2/RTU */
    { 0x33, 0x000040 }, /* PLL1_3/APU: 64 samples if APD remains 0 */
    { 0x34, 0x000000 }, /* PLL1_4/FSD: saw-tooth candidate, verify by GUI export */
    { 0x35, 0x000000 }, /* PLL1_5/RSD: saw-tooth candidate, verify by GUI export */
    { 0x36, 0x000000 }, /* PLL1_6/RTD: saw-tooth candidate, verify by GUI export */
};
```

写入函数建议：

```c
static sr_t AppRadarDebugAcquisition_writeProfile(IRadarAvian *radar)
{
    IRegisters8_32 *registers = radar->getIRegisters(radar);

    for (uint32_t i = 0; i < ARRAY_SIZE(g_profile); i++)
    {
        RETURN_ON_ERROR(registers->write(registers, g_profile[i].address, g_profile[i].value));
    }

    return E_SUCCESS;
}
```

实现前检查点：

- GUI 导出文件中的寄存器地址和值必须完整保存到本文档或独立 `.md`/`.csv`。
- 可以用数据手册公式核对 `FSU/RSU/RTU/APU`，但不要只根据 GUI 参数文本手算整套 profile。
- 不允许只写 `DataAvian_configure(...)` 而跳过 BGT60TR13C profile 寄存器写入。
- 保留 reserved bit 的默认状态，不要为了“凑参数”改 RSVD 位。

## DataAvian 读数配置

`DataAvian_configure(...)` 只负责 MCU 如何从 BGT FIFO 读取数据，不负责生成 chirp profile。它必须在寄存器 profile 写入后配置。

第一版推荐使用 `DataFormat_Packed12`，因为 BGT 原始 ADC 是 12-bit，payload 更小，预期一帧：

```text
64 samples/chirp * 64 chirps/frame * 3 RX * 1.5 bytes = 18432 bytes
```

对应 `IDataProperties_t`：

```c
IDataProperties_t properties = {
    .format          = DataFormat_Packed12,
    .rxChannels      = 3,
    .ramps           = 64,
    .samples         = 64,
    .channelSwapping = 0,
    .bitWidth        = 12,
};
```

如果需要验证 Raw16，则预期一帧：

```text
64 samples/chirp * 64 chirps/frame * 3 RX * 2 bytes = 24576 bytes
```

Raw16 对应：

```c
properties.format = DataFormat_Raw16;
```

DataAvian settings 建议按“一次 IRQ 读取一个 chirp，聚合 64 个 chirp 成一帧”设计。FIFO access 地址来自数据手册 register list，第一版用 `0x60`：

```c
static const uint16_t readouts[][2] = {
    { 0x0060u, 64u * 3u },
};

uint8_t settings[DATA_SETTINGS_BGT_RADAR_SIZE(ARRAY_SIZE(readouts), 64u)];
DataSettingsBgtRadar_initialize(settings, readouts, ARRAY_SIZE(readouts), 64u);
```

说明：

- 第一行第二列是单次 readout 的 12-bit sample 数：`64 samples * 3 RX = 192`。
- `DataSettingsBgtRadar_initialize(...)` 会在末尾追加 aggregation entry；源码里 `lastEntry[1] == 0` 时，`aggregation = lastEntry[0] + 1`，所以 `64` 会被编码成 `63, 0`。
- 实际传入 `DataAvian_configure(...)` 的 settings 字节序是 little-endian，Packed12 第一版对应：`60 00 C0 00 3F 00 00 00`。
- `DataAvian_configure(...)` 在 `DataFormat_Packed12` 下会把 `readoutCount=192` 转成 `288 bytes` 的 slice size；聚合 64 个 slice 后得到 `288 * 64 = 18432 bytes`。
- `DataAvian_configure(...)` 在 `DataFormat_Raw16` 下会把 `readoutCount=192` 转成 `384 bytes` 的 slice size；聚合 64 个 slice 后得到 `384 * 64 = 24576 bytes`。

## 推荐接口

`AppRadarDebugAcquisition.h` 建议提供：

```c
void AppRadarDebugAcquisition_Constructor(IRadarAvian *radar, IData *data, uint8_t dataIndex);
void AppRadarDebugAcquisition_run(void);
void AppRadarDebugAcquisition_stop(void);
bool AppRadarDebugAcquisition_isRunning(void);
```

职责说明：

- `Constructor`：保存雷达组件、数据接口和 dataIndex。
- `run`：只在 DEBUG_TEXT 下执行一次内部配置和启动，后续立即返回。
- `stop`：切换到 HOST_PROTOCOL 前停止内部采集。
- `isRunning`：便于调试和后续模式切换保护。

`BoardOutput.h` 建议补充只读模式查询：

```c
BoardOutput_Mode_t BoardOutput_getMode(void);
```

这样 `AppRadarDebugAcquisition_run()` 可以判断当前是否允许内部自动采集，而不是访问 `BoardOutput.c` 内部静态变量。

## 启动顺序

推荐内部启动顺序：

1. 确认 `BoardOutput_getMode() == BOARD_OUTPUT_MODE_DEBUG_TEXT`。
2. 确认 `IRadarAvian *radar != NULL`，`IData *data != NULL`。
3. 调用 `radar->stopData(radar)`，确保不是运行中状态；这一步会置位 `MAIN.FIFO_RESET | MAIN.FSM_RESET`。
4. 写入 `SFCTL = 0x100000`，保持当前固件已验证过的高速 SPI/FIFO 控制设置。
5. 写入 GUI 导出的 BGT60TR13C profile 寄存器表，至少覆盖 `PACR1/PACR2/CSU1/CSC1/CCR0..CCR3/PLL1_0..PLL1_7`。
6. 调用 `radar->initialize(radar)`。
7. 调用 `data->configure(dataIndex, &properties, settings, sizeof(settings))`。
8. 调用 `radar->startData(radar)`，内部会先 `IData.start()`，再置位 `MAIN.FRAME_START`。
9. 打印 `debug-acq,start,ok`。
10. 等待 `DataAvian_run()` 在主循环中聚合满一帧后回调 `Board_dataCallback(...)`。

对应最小代码骨架：

```c
static sr_t AppRadarDebugAcquisition_start(void)
{
    RETURN_ON_ERROR(m_radar->stopData(m_radar));
    RETURN_ON_ERROR(AppRadarDebugAcquisition_writeProfile(m_radar));
    RETURN_ON_ERROR(m_radar->initialize(m_radar));
    RETURN_ON_ERROR(m_data->configure(m_dataIndex, &properties, settings, sizeof(settings)));
    RETURN_ON_ERROR(m_radar->startData(m_radar));

    return E_SUCCESS;
}
```

## HOST_PROTOCOL 保护

切换到官方上位机协议前，必须停止内部调试采集：

```text
/mode host
  -> AppRadarDebugAcquisition_stop()
  -> BoardOutput_setMode(BOARD_OUTPUT_MODE_HOST_PROTOCOL)
  -> ProtocolHandler_run()
```

保护规则：

- `HOST_PROTOCOL` 下不自动启动内部采集。
- `HOST_PROTOCOL` 下不输出普通文本。
- `HOST_PROTOCOL` 由官方上位机重新配置雷达和启动采集。
- 如果内部采集未停止就切 host，可能导致官方上位机以为设备空闲，但雷达和 DataAvian 已经处于运行状态。

## 多 Subagent 分工

后续实现时使用多 subagent，但 Root 主控集成者负责最终判断。

### Root 主控集成者

- 冻结 GUI 寄存器导出文件。
- 决定 `Packed12` 还是 `Raw16` 作为第一版默认格式，默认推荐 `Packed12`。
- 合并实现、审查和构建结果。
- 判断是否可以烧录测试。

### 实现 Agent

- 只负责 `AppRadarDebugAcquisition.c/.h`、必要的 `Board.c` 接入、必要的 `BoardOutput_getMode()`。
- 不改 HAL、ASF、CMSIS、SPI、DMA。
- 不改官方协议层源码。

### 审查/测试 Agent

- 检查寄存器写入顺序是否来自 GUI 导出。
- 检查 `DataAvian_configure(...)` 的 `settings` 和 `aggregation` 是否正确。
- 检查 HOST_PROTOCOL 切换前是否停止内部采集。
- 检查 `Board_dataCallback(...)` 打印是否限频，不刷屏。

### 构建验证 Agent

- 确认新 `.c/.h` 加入 Atmel Studio 工程和 Makefile 构建。
- 确认使用 Atmel Studio ARM GCC 6.3.1。
- 验证 Release/Debug 编译。
- 检查 `.bin/.elf/.map` 是否生成。

### 专项分析 Agent

需要时只读分析：

- BGT60TR13C FIFO readout address。
- Radar Fusion GUI 导出寄存器序列格式。
- `DataAvian_configure(...)` settings 与官方上位机下发配置的对应关系。

## 验证计划

第一轮验证：

- 不打开 Radar Fusion GUI。
- 只打开串口助手。
- 上电后能看到 `debug-acq,config,start`。
- 能看到 `debug-acq,start,ok`。
- 能看到 `probe,...cnt=18432...fmt=packed12`。
- `dt` 接近 `77300 us`。

第二轮验证：

- 输入 `/mode host`。
- 固件先停止内部采集。
- 普通文本停止输出。
- 再打开官方上位机，确认官方协议可以重新连接、配置和采集。

失败时优先看：

- 是否没有写入完整 BGT60TR13C profile。
- `FIFO_READOUT_ADDRESS` 是否错误。
- `DataAvian_configure(...)` 是否返回失败。
- `settings` 是否没有正确设置 aggregation。
- `.c` 文件是否没有加入工程构建。
- USB 文本输出是否过快导致主循环影响采集。

## 当前阶段边界

本技能文档只规划“内部启动采集调试入口”。当前不直接实现：

- 生命体征算法。
- Range FFT。
- 完整 radar cube。
- 官方上位机协议扩展。
- HAL/SPI/DMA 底层改造。

后续源码实现必须以 GUI 导出的寄存器序列为准。没有寄存器导出文件前，只允许搭建模块结构和 DataAvian 配置框架，不允许写入猜测寄存器值。
